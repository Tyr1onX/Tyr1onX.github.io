# 当 AI 开始“磨洋工”：一次 GitHub 工具失效的排查与复盘

在使用 ChatGPT 协助开发项目时，我遇到过一种非常令人困惑的情况：

明明已经明确要求它进入 GitHub 仓库修改代码，它却不断重复我的要求、承认自己做错了、解释接下来准备做什么，但始终不真正调用 GitHub 工具。

更奇怪的是，这个问题主要发生在手机端。一开始，手机端明明可以正常读取并修改 GitHub 仓库；但一旦进入这种“只说不做”的状态，之后无论怎样催促，似乎都很难恢复。切换到电脑网页端后，同一个任务却往往可以重新正常执行。

这次经历让我意识到：和 AI 协作时，不仅要判断它给出的结果是否正确，还要判断它是否真的进入了执行状态。

---

## 一、问题是怎样出现的

正常情况下，我会给 ChatGPT 一个比较明确的开发任务，例如：

* 进入指定 GitHub 仓库；
* 读取最新代码；
* 定位某个界面或资源问题；
* 修改代码；
* 测试并提交。

在状态正常时，它会直接调用 GitHub 工具，读取仓库文件，然后继续修改。

但在异常状态下，它的回复会变成这样：

* “你说得对。”
* “我理解你的要求了。”
* “这次我会真正解决。”
* “接下来我会先检查代码。”
* “问题可能出在图片缓存或资源引用上。”

这些话看上去像是在推进任务，但实际上没有任何工具调用，也没有读取新的仓库内容。

当我指出它没有执行时，它又会继续解释为什么刚才没有执行。于是对话逐渐进入一个循环：

> 没有执行 → 被指出 → 道歉和解释 → 承诺执行 → 仍然没有执行。

我把这种状态称为 AI 的“磨洋工状态”。

---

## 二、这不只是 GitHub 权限问题

最开始，很容易把问题归结为：

* 手机端不支持 GitHub 修改；
* GitHub 权限失效；
* 手机缓存异常；
* 网络连接不稳定。

但这些解释并不能完整说明现象。

因为同一个手机端，在其他时候确实可以正常修改仓库。这意味着：

* GitHub 授权本身并没有永久失效；
* 手机端并非完全不具备仓库修改能力；
* 我的指令也不是天然无法触发工具；
* 问题不是简单的“手机端不支持”。

更加关键的现象是：

> 一旦当前对话开始持续不调用工具，后续就很难靠继续催促恢复；但切换到电脑网页端后，往往又能正常工作。

因此，更合理的判断是：问题不是单纯的权限缺失，而是当前客户端或当前对话的工具执行状态发生了异常。

---

## 三、我的判断：工具状态异常和对话惯性叠加

我无法查看 ChatGPT 内部的运行日志，因此不能断言后台具体发生了什么。但根据实际表现，可以提出一个比较符合现象的解释：

### 1. 工具执行状态可能失效

手机端在某一次工具调用、上下文切换或任务处理中，可能没有正确进入 GitHub 工具执行流程。

工具没有成功触发后，系统退回了普通文本回答。

于是，本来应该执行的动作：

> 读取仓库 → 修改文件 → 提交代码

被替换成了：

> 描述将如何读取仓库 → 分析可能的问题 → 承诺稍后修改。

用户看到的结果就是：它一直在说自己要做什么，却没有真正开始。

### 2. 对话会延续前面的行为模式

语言模型在生成下一条回复时，会参考前面的对话。

如果上一轮没有调用工具，而是解释和道歉，下一轮就可能继续沿用这个模式。

当用户不断说：

* “不要解释了。”
* “赶紧去 GitHub。”
* “为什么还没有开始？”
* “我已经说得很清楚了。”

模型可能错误地把重点识别成：

> 用户正在批评我的沟通方式，我应该先回应他的不满。

结果，它继续解释、认同和道歉，而不是重新进行一次独立的工具判断。

这形成了一种对话惯性：

> 第一次选错了响应模式，后续内容又不断强化这个错误模式。

### 3. 手机端和网页端可能重新建立不同的执行上下文

当我切换到电脑网页端时，客户端可能会重新加载：

* 当前可用的工具；
* GitHub 连接状态；
* 当前会话的工具环境；
* 消息与工具之间的路由状态。

因此，即使还是同一个任务，网页端也可能重新建立一套正常的执行入口。

这可以解释为什么：

> 手机端已经“卡死”的任务，切到电脑端后却可以重新正常调用 GitHub。

---

## 四、最大的误区：试图通过继续对话把它“骂醒”

这次经历中，我做得最无效的一件事，就是在它已经进入异常状态后，不断继续纠正它。

我会反复告诉它：

* 不要再解释；
* 不要重复我的话；
* 现在就去 GitHub；
* 你又没有调用工具；
* 不要假装正在处理。

这些要求本身没有问题，但当当前会话已经进入错误轨道时，继续发送这些内容往往只会产生更多解释。

对话会越来越长，情绪信息越来越多，而真正的开发任务反而被埋在后面。

最后出现一种非常荒谬的情况：

> 用户花了大量时间要求 AI 开始工作，而 AI 花了大量文字解释自己为什么还没有开始工作。

这说明，在 AI 工具协作中，“继续沟通”并不总能修复问题。有时最有效的操作是直接终止当前执行环境，重新开始。

---

## 五、如何判断 AI 是否真的开始工作

以后再处理 GitHub 任务时，我会使用一个非常简单的判断标准：

> 不看它说了什么，只看有没有出现可验证的工具结果。

真正开始工作，至少应当出现以下内容之一：

* 读取了具体仓库；
* 显示了当前分支；
* 获得了最新 commit；
* 打开了具体文件；
* 搜索了某段代码；
* 返回了 GitHub 工具错误；
* 创建了分支；
* 产生了 diff；
* 提交了 commit；
* 创建了 Pull Request。

而下面这些内容全部不算执行：

* “我现在开始检查。”
* “这次会彻底解决。”
* “我理解你的意思。”
* “问题应该出在……”
* “接下来我会……”
* “你说得完全正确。”

没有工具调用，就没有开始。

## 六、以后采用的处理流程

为了避免再次在异常对话中浪费时间，我给自己制定了一套处理规则。

### 第一步：只允许失败一次

明确要求执行 GitHub 任务后，如果第一轮没有调用工具，只再发送一次强制执行指令：

> 停止解释，不要复述要求。下一步必须调用 GitHub 工具读取仓库。只有工具调用失败时，才允许用文字说明具体错误。

如果下一轮依然只是普通文字回复，就不再继续纠正。

### 第二步：重新挂载工具

在手机端尝试：

* 退出当前对话后重新进入；
* 重新选择 GitHub 工具；
* 使用 `@GitHub` 明确指定；
* 重新发送一个只包含仓库和第一步动作的短指令。

重点不是继续补充需求，而是重新建立工具执行状态。

### 第三步：强制关闭并重新打开客户端

如果重新进入对话仍然没有恢复，就彻底关闭手机 App，再重新打开。

普通缓存清理未必有用，因为问题可能不在图片缓存或本地文件缓存，而在当前会话与工具之间的运行状态。

### 第四步：新建对话

如果还是无法执行，就立即新建聊天，不再保留原对话中的错误惯性。

新的交接内容只保留：

* 仓库地址；
* 当前分支；
* 当前问题；
* 相关文件；
* 已经尝试过的修改；
* 第一条必须执行的动作。

不要把几十轮争论、解释和失败过程全部复制进去，否则新的对话又会先处理历史，而不是处理代码。

### 第五步：切换到电脑端

当任务比较重要，或者手机端连续异常时，直接切换到电脑网页端。

这不是因为电脑端一定更聪明，而是电脑端可能重新建立工具运行环境，从而绕过手机端已经失效的执行状态。

---

## 七、推荐使用的 GitHub 执行提示词

以后开始仓库任务时，可以使用这样的指令：

> 这是一个需要直接执行的 GitHub 任务，不是方案讨论。
> 第一条动作必须是调用 GitHub 工具读取默认分支、最新提交和相关文件。
> 不要重复确认已经明确的要求，不要先解释计划。
> 如果当前没有 GitHub 访问或写入能力，直接说明缺少的具体能力。
> 读取完成后，根据实际代码修改、测试并提交。

这段提示词不能保证工具永远不出问题，但它能建立一个清晰的验收标准：

> 要么调用工具，要么明确报告无法调用。

不允许用“准备执行”代替执行。

## 八、这次经历带来的更一般的启发

这不仅是一个 GitHub 工具问题，也反映了人与 AI 协作中的几个普遍问题。

### 1. AI 的表达流畅，不代表任务正在推进

AI 非常擅长生成看似合理的计划、解释和反思。

因此，使用 AI 做实际工作时，不能只根据语言判断进度，而要检查外部状态是否发生变化。

例如：

* 文件是否修改；
* 测试是否运行；
* commit 是否产生；
* Issue 是否更新；
* 日历事件是否创建；
* 邮件是否真正发送。

AI 的语言只能作为说明，不能作为执行证明。

### 2. 对 AI 的纠错也需要成本控制

当 AI 连续两次没有执行时，继续与它争论通常不是最优选择。

人容易产生一种心理：

> 我已经解释得这么清楚了，再说一次它应该就能明白。

但工具状态异常时，问题并不在于它是否理解，而在于它是否能够或是否正确进入执行流程。

此时最重要的不是继续教育当前会话，而是重建工作环境。

### 3. 长对话不是永久可靠的工作空间

长对话能够保存上下文，但也会积累：

* 过时的设计决策；
* 已经失效的代码状态；
* 多轮失败记录；
* 情绪化纠正；
* 相互矛盾的要求。

因此，项目开发不能完全依赖一个无限延长的聊天窗口。

更可靠的方式是把真正的项目状态保存在：

* GitHub Issues；
* README；
* 项目文档；
* commit；
* PR 描述；
* 独立的交接说明。

聊天应该是执行入口，而不是唯一的项目记忆。

### 4. AI 协作需要“可验证的下一步”

一个好的 AI 任务，不只是描述最终目标，还要规定第一步必须产生什么证据。

例如：

* 先读取仓库；
* 先列出当前分支和 commit；
* 先打开指定文件；
* 先运行测试；
* 先展示 diff。

当第一步是可验证的，就能很快判断 AI 是在工作，还是只是在生成语言。

---

## 九、最终结论

这次问题并不是简单的“手机端不能用 GitHub”，因为手机端在正常状态下确实能够修改仓库。

更加符合实际现象的解释是：

> 手机端当前会话的工具执行状态发生异常，GitHub 调用没有正确触发；随后模型又受到前文影响，持续进入解释、认同和道歉的对话模式，形成了很难自行恢复的行为惯性。

切换到电脑网页端能够恢复，说明问题更可能发生在客户端或会话级执行环境，而不是仓库权限永久失效。

这次经历最终让我形成了一条最重要的原则：

> 当 AI 应该执行工具任务时，不要听它如何描述自己的行动，只检查它是否产生了真实、可验证的工具结果。

一旦发现它开始“磨洋工”，不要在原地无限纠正。

只允许一次恢复尝试，然后立刻重新挂载工具、重启客户端、新建对话或切换设备。

和 AI 协作的效率，不仅取决于如何提出要求，也取决于能否及时识别：当前问题究竟是任务难，还是执行环境已经失效。
